## 保留的技術債與處理次序

1. **controller 責任偏大、原始碼長行多。** portal.js 同時管頁面、操作、存檔及對話；CSS 存在歷史覆寫。先在需要改動的函式範圍整理可讀性，再拆純 renderer／儲存 adapter。不要整倉格式化掩蓋功能差異。
2. **兩個 UI controller。** 原作與長篇有不同 action attribute／存檔；目前保留雙路徑與真實 iframe 測試。共用功能先放 FieldUI／Cinema；未設計遷移前不強行合併 state。
3. **載入時方法包裝。** Pressure／Theatre 對順序敏感，重複載入無防護。本次以入口清單守住單次載入；未來熱更新或插件系統應先改為明確組装方法並測試。
4. **查詢不全是純函式。** Chronicles.memory、Pressure.ensure／describe 可能初始化欄位；不能只憑名字假定只讀。後續拆分時應逐步做 immutable view model，不在本次貿然改遊戲語義。
5. **故事識別散布。** 新故事需同步 UI、圖片、危機、驗證、recap 與建置。列出完整清單，比現在引入另一份不完整「唯一故事登錄」更可靠；未來可集中並產生入口。
6. **測試編排仍有重複。** Node、browser runtime、WinForms 注入各有用途；完整驗收固定走 verify，未把所有 runner 改寫。
7. **桌面自檢與產品殼同檔。** 本次只抽出結果判定；未來測試增加可再抽出 runner class。未測試全新機器與實體跨 DPI 螢幕拖曳。
